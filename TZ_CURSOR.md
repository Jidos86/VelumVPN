# ТЗ: Стабилизация ядра mihomo + уменьшение веса приложения VelumVPN

Контекст: Electron-десктоп-клиент (форк koala-clash), оборачивает процесс mihomo (clash-meta core). За последнее время участилось "случайное" поведение — ядро не стартует / зависает в состоянии "подключено" при мёртвом процессе, редко — падение всего приложения. Плюс отдельная задача — снизить объём устанавливаемого приложения.

Ниже — приоритизированный список задач. Каждая задача содержит: файл(ы), текущее поведение, что нужно сделать, критерий приёмки. Не трогать код за пределами описанного скоупа задачи — без рефакторинга "заодно".

---

## Блок A. Стабильность ядра (приоритет — сделать первым)

### A1. Сериализация операций над ядром (startCore/stopCore/restartCore)

**Файл:** `src/main/core/manager.ts`

**Проблема:** `child` — модульная переменная (`let child: ChildProcess`, строка ~71), присваивается напрямую в `startCore()`. Вызовы `startCore`/`stopCore`/`restartCore` идут минимум из 5 независимых мест без какой-либо блокировки:
- IPC-хендлер `restartCore` (`src/main/utils/ipc.ts`)
- авто-восстановление в `child.on('close', ...)` (manager.ts ~166-190)
- `setInterval` определения сети (manager.ts ~653-668)
- `config/profile.ts`: `changeCurrentProfile`, `removeProfileItem`, `setProfileStr`
- `core/profileUpdater.ts` (таймер авто-обновления профиля)

Два параллельных вызова могут перезаписать `child` раньше, чем первый успеет корректно остановить старый процесс → осиротевший mihomo, занятый control-socket → ошибка `External controller ... listen error` или зависшее "подключено" в UI при мёртвом ядре.

**Что сделать:**
1. Добавить единую точку сериализации для `startCore`/`stopCore`/`restartCore` — например, простую async-очередь/мьютекс на уровне модуля (одна операция над ядром выполняется полностью, следующая ждёт её завершения; конкурентные вызовы `restartCore()`, поданные пока другой restart уже выполняется, должны схлопываться в один — не накапливать очередь идентичных перезапусков).
2. Все вызывающие места (IPC-хендлер, авто-restart при close, network-interval, profile.ts, profileUpdater.ts) должны идти через одну и ту же обёрнутую точку входа, не напрямую манипулировать `child`.
3. Не менять публичный API этих функций (сигнатуры, возвращаемые типы) без необходимости — только внутреннюю синхронизацию.

**Критерий приёмки:**
- Быстрые повторные клики "переподключиться" в UI не оставляют осиротевших процессов mihomo (проверить `tasklist`/`ps` до/после серии из 10 быстрых кликов).
- Искусственный сценарий: вызвать `restartCore()` и сразу `changeCurrentProfile()` — не должно быть двух параллельно запущенных процессов ядра.

### A2. Обработчик `'error'` на spawn ядра

**Файл:** `src/main/core/manager.ts`, около строки 143 (`child = spawn(corePath, [...], {...})`)

**Проблема:** зарегистрирован только `child.on('close', ...)`. При ошибке самого spawn (бинарник в карантине антивируса, файл отсутствует, EPERM/SUID) Node эмитит `'error'`, необработанное событие `'error'` на EventEmitter — исключение, способное уронить весь main-процесс Electron без диалога пользователю.

**Что сделать:**
- Добавить `child.on('error', (err) => {...})` сразу после `spawn(...)`, до любых await/return.
- В обработчике: залогировать ошибку в `logPath()` (тем же способом, что и `close`-обработчик), показать пользователю тот же/аналогичный диалог, что и при исчерпании retry в `close`-хендлере (`dialog.showMessageBox` с `coreCrashRecovery`), не дать необработанному исключению всплыть.
- Учесть, что `'error'` и `'close'` могут прийти оба на один и тот же spawn-fail — не показывать пользователю два диалога подряд.

**Критерий приёмки:**
- Переименовать/удалить бинарник ядра (`mihomo.exe`) перед запуском `startCore()` — приложение не крашится, показывает диалог ошибки.

### A3. Backoff при авто-restart после краша

**Файл:** `src/main/core/manager.ts`, `child.on('close', ...)` (~166-190)

**Проблема:** `retry--; await restartCore()` — без задержки между попытками. До 10 попыток подряд без паузы при системной проблеме (битый конфиг, занятый порт) — лишняя нагрузка на CPU/диск перед финальным диалогом.

**Что сделать:**
- Добавить возрастающую задержку между попытками (например: 500мс, 1с, 2с, 4с... с потолком в районе 5-10с), либо фиксированную паузу 1-2с — простое решение приоритетнее сложного экспоненциального алгоритма.
- Не менять итоговое количество попыток (10) и финальный диалог при их исчерпании.

**Критерий приёмки:** серия крашей ядра подряд не производит 10 рестартов за доли секунды — видна пауза между попытками в логе (`logPath()`).

### A4. Реальный fallback-источник геоданных

**Файл:** `src/main/core/factory.ts`, ~строки 47-76 (`RUNETFREEDOM_FALLBACK_URLS`, `downloadWithFallback`)

**Проблема:** `RUNETFREEDOM_FALLBACK_URLS` равен основному `RUNETFREEDOM_URLS` — фолбэк никогда не срабатывает (`fallbackUrl !== primaryUrl` всегда false). При недоступности GitHub Releases обновление правил маршрутизации тихо не происходит (ошибка гасится в catch в `ensureRunetfreedomGeodata()`, ~строка 208).

**Что сделать:**
1. Указать реальный альтернативный источник для `geosite.dat`/`geoip.dat` (например, зеркало на jsDelivr для CDN, отличное от заблокированного домена, или иной раздатчик тех же файлов из репозитория `runetfreedom/russia-v2ray-rules-dat` — уточнить у пользователя рабочий актуальный источник перед реализацией, если неочевидно из истории коммитов, т.к. jsDelivr ранее убрали намеренно как заблокированный в РФ).
2. В `ensureRunetfreedomGeodata()` при неудаче скачивания — не просто гасить ошибку в catch: залогировать и, если ни основной, ни fallback источники недоступны, уведомить пользователя (не блокирующий тост/лог в UI), что геоданные не обновлены и используется предыдущая локальная копия.

**Критерий приёмки:** при заблокированном/недоступном основном URL (смоделировать через hosts-файл или временную подмену URL) обновление геоданных всё равно завершается успешно через фолбэк, либо явно сообщает пользователю о неудаче вместо молчаливого пропуска.

### A5. Синхронизация таймера авто-обновления профиля со стартом ядра

**Файл:** `src/main/core/profileUpdater.ts`, `src/main/index.ts` (~320-332)

**Проблема:** `initProfileUpdater()` запускается параллельно с `startCore()` на фиксированных задержках (`START_DELAY_MS = 10_000`, `STARTUP_REFRESH_DELAY_MS = 60_000`) вместо ожидания реальной готовности ядра. При медленном старте (~>10с) первый тик обновления профиля может вызвать `restartCore()` пока предыдущий `startCore()` ещё не завершился.

**Что сделать:**
- Заменить фиксированную задержку на ожидание фактического события готовности ядра (использовать существующий механизм `waitForMihomoReady()`/событие `core-started`, уже используемый в `manager.ts`), чтобы `profileUpdater` не начинал тикать, пока ядро не подтвердило готовность.
- Не убирать `STARTUP_REFRESH_DELAY_MS` как концепцию — оставить как таймаут для последующих обновлений, менять только startup-путь.

**Критерий приёмки:** при искусственно замедленном старте ядра (например, временный `await sleep(15000)` в начале `startCore` для теста) первый тик `profileUpdater` не запускается раньше, чем ядро реально готово.

### A6. Command injection в convertMrsRuleset

**Файл:** `src/main/config/profile.ts`, ~строка 462:
```ts
await execAsync(`"${corePath}" convert-ruleset ${behavior} mrs "${fullPath}" "${tempFilePath}"`)
```

**Проблема:** `fullPath` приходит из IPC-запроса рендерера без экранирования, подставляется в shell-строку через `exec()`.

**Что сделать:** заменить `exec()`/`execAsync()` на `execFile()`/`execFilePromise()` с аргументами массивом (`[corePath, 'convert-ruleset', behavior, 'mrs', fullPath, tempFilePath]`) — без прохода через shell, инъекция становится невозможна независимо от содержимого путей.

**Критерий приёмки:** конвертация ruleset продолжает работать на обычных путях; путь с кавычками/спецсимволами (`"; echo pwned; "`) не приводит к выполнению постороннего кода (просто ошибка "файл не найден" или аналог).

## Блок B. Уменьшение веса приложения

### B1. Не копировать/не хранить неиспользуемый формат геоданных

**Файл:** `src/main/utils/init.ts`, `initFiles()` ~строки 85-114

**Проблема:** безусловно копируются **все 5** файлов (`country.mmdb`, `geoip.metadb`, `geoip.dat`, `geosite.dat`, `ASN.mmdb`) при каждом старте приложения — причём **дважды**: в `mihomoWorkDir()` и в `mihomoTestDir()`. При этом реально используется одновременно только один формат (mmdb ИЛИ dat) в зависимости от `geodata-mode`.

**Что сделать:**
1. Определить активный `geodata-mode` (см. использование в `factory.ts`/`config/app.ts`) до копирования.
2. Копировать в `mihomoWorkDir()`/`mihomoTestDir()` только файлы активного формата: mmdb-режим → `country.mmdb` + `geoip.metadb` (+ `ASN.mmdb`, если фича ASN включена отдельно — проверить, действительно ли ASN нужен всегда или тоже опционален); dat-режим → `geoip.dat` + `geosite.dat`.
3. При переключении режима в настройках — докопировать недостающий файл в этот момент (не требовать перезапуска приложения, если возможно без большой переделки; если требует — зафиксировать это как известное ограничение и явно сообщить в UI).
4. Не менять сам механизм `shouldCopy` (сравнение по размеру) — только список копируемых файлов.

**Критерий приёмки:** после чистой установки и первого запуска в `mihomoWorkDir()`/`mihomoTestDir()` лежат только файлы активного на данный момент режима геоданных, не все пять.

### B2. Не бандлить оба ядра (mihomo + mihomo-alpha) по умолчанию

**Файлы:** `scripts/prepare.mjs` (сборка), `src/main/core/manager.ts` / `src/main/utils/init.ts` (рантайм-логика выбора ядра, `mihomoCorePath`)

**Проблема:** `prepare.mjs` всегда скачивает и бандлит оба бинарника ядра (`mihomo` и `mihomo-alpha`), хотя канал alpha — опциональный переключатель в настройках, которым пользуется меньшинство. Плюс ~20-40 МБ на бинарник ядра x2.

**Что сделать:**
1. В `prepare.mjs`: по умолчанию (без явного флага/env) собирать только `mihomo` (stable). Добавить возможность собрать alpha отдельно (например, `INCLUDE_ALPHA_CORE=1` в env) — для CI/ручной сборки, если alpha всё же нужно поставлять part of бандла для части каналов дистрибуции.
2. В рантайме (там, где приложение переключает канал ядра на alpha, вероятно в настройках/`manualGrantCorePermition`) — если бинарника `mihomo-alpha` нет на диске, скачать его по требованию (переиспользовать логику скачивания+распаковки zip/gz из `prepare.mjs`, вынесенную в переиспользуемую функцию/модуль, доступную и сборочному скрипту, и рантайму — либо продублировать компактную версию именно под Electron main process, если делить модуль между build-time ESM скриптом и Electron рантаймом неудобно).
3. Показать пользователю прогресс/лоадер во время докачки alpha-ядра при первом переключении канала.

**Критерий приёмки:** свежая сборка/установка не содержит `mihomo-alpha` бинарника, пока пользователь явно не переключился на alpha-канал в настройках — после переключения ядро скачивается и работает штатно.

### B3. Ленивая загрузка редактора Monaco

**Файлы:** места использования `react-monaco-editor`/`monaco-yaml` в `src/renderer/src` (найти через grep по `monaco` в `src/renderer`)

**Проблема:** `monaco-editor` + `monaco-yaml` + `react-monaco-editor` — один из самых тяжёлых кусков JS-бандла, нужен только на странице редактирования YAML-шаблонов маршрутизации, не на каждом экране.

**Что сделать:**
- Убедиться, что компонент(ы), использующие Monaco, подключены через `React.lazy()`/динамический `import()`, а не статический импорт в общем бандле — так, чтобы chunk с Monaco загружался только при реальном открытии редактора шаблонов, а не при старте приложения.
- Если уже так сделано (проверить перед началом работы) — задачу закрыть без изменений, зафиксировав, что уже оптимально.

**Критерий приёмки:** в build-выводе (`out/renderer` после `pnpm build`) Monaco-related код лежит в отдельном chunk-файле, не входящем в основной/начальный бандл (проверить через анализ `out/renderer/assets/*.js` размеров и/или `--report` от Vite, если доступно).

### B4. Дедупликация иконок

**Файлы:** `build/*.png`, `build/icons/*`, `resources/*.png`, `resources/*.ico`

**Проблема:** несколько идентичных по размеру PNG/ICO дублируются между `build/` и `resources/` (например `build/icon.png` и `build/icon_1024.png` оба 280K, `resources/icon.png`/`resources/icon_off.png`/`resources/icon.ico`/`resources/icon_off.ico` частично дублируют `build/icons/*`).

**Что сделать:**
- Свести к одному источнику правды на каждый размер/формат иконки, убрать явные дубликаты файлов с одинаковым содержимым (сравнить по хэшу `sha256sum`/`Get-FileHash`, не полагаться только на совпадение размера в байтах).
- Обновить ссылки в `electron-builder.yml`/коде на актуальные оставшиеся пути.

**Критерий приёмки:** сборка под все текущие таргеты (win/mac/linux) проходит без ошибок отсутствия иконок, итоговый размер `build/`+`resources/` меньше текущего (798К + 2.4М).

## Общие ограничения для исполнителя (Cursor)

- Не делать рефакторинг за пределами описанного скоупа каждой задачи.
- Не менять публичные сигнатуры IPC-хендлеров (`src/shared/types/*`) без явной необходимости — рендерер их использует.
- Каждую задачу — отдельным коммитом с понятным сообщением (`fix: ...` для блока A, `perf: ...`/`build: ...` для блока B).
- Для задач блока A, где есть numeric-константы (retry count, delays) — не менять их значения сверх того, что явно описано в задаче.
- Комментарии в коде — только там, где неочевидна причина (WHY), не описывать что делает код.
