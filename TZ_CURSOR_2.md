### C1. `initProfileUpdater` может зависнуть навсегда, если ядро так и не стартовало

**Файл:** `src/main/core/profileUpdater.ts:68-75`

**Проблема:**
```ts
export async function initProfileUpdater(): Promise<void> {
  if (started) return
  started = true
  setTimeout(runStartupRefresh, STARTUP_REFRESH_DELAY_MS)
  void waitForCoreReady().then(() => {
    void runTick()
  })
}
```
`waitForCoreReady()` (`manager.ts:86-98`) резолвится только через `signalCoreReady()` при успешном старте ядра. Если ядро не смогло стартовать (исчерпаны retry из задачи A3, показан `showCoreCrashDialog`) — этот промис не резолвится никогда, и `runTick()` не запускается за всю сессию приложения, даже если пользователь потом вручную это исправит.

**Что сделать:**
- Не ждать `waitForCoreReady()` бесконечно. Использовать гонку (`Promise.race`) между `waitForCoreReady()` и таймаутом (например, 30-45 секунд) — какое событие наступит раньше, то и триггерит первый запуск `runTick()`.
- Учесть, что фактическая цель синхронизации со стартом ядра (задача A5 из первого ТЗ) уже подстрахована локом из задачи A1 (`withCoreLock` в `manager.ts` сериализует все операции над ядром) — поэтому таймаут-фолбэк здесь безопасен: `runTick()`, вызванный до полной готовности ядра, просто встанет в очередь лока, а не сломает состояние.
- Не убирать сам механизм ожидания готовности ядра как оптимизацию (полезно в штатном случае) — только добавить границу по времени.

**Критерий приёмки:** смоделировать ситуацию, когда `signalCoreReady()` никогда не вызывается (ядро не стартует) — `runTick()` всё равно запускается не позже, чем через выбранный таймаут, не зависает на весь сеанс.

### C2. Хендлер `'updater: finished'` вызывает залоченные функции изнутри незавершившегося залоченного вызова

**Файл:** `src/main/core/manager.ts:257-277`

**Проблема:** блок, реагирующий на `'updater: finished'` в stdout, вызывает `stopCore(true)` и `startCore()` — экспортируемые версии, обёрнутые в `withCoreLock` (`manager.ts:480-486`). Но сам этот код исполняется **внутри** ещё не завершившегося исполнения `startCoreUnlocked()` (мы находимся в executor'е промиса, который эта функция возвращает, до того как он resolve/reject). Поскольку `withCoreLock` сериализует через `coreOpChain = coreOpChain.then(fn)`, новый вызов `stopCore(true)` встаёt в очередь **за самим собой** — выполнится только после того, как текущий (внешний) залоченный вызов settle'ится. Одновременно `'close'`-хендлер (после того как процесс реально завершится вслед за печатью `'updater: finished'`) тоже инициирует restart через `withCoreLock(restartCoreUnlocked)` с новым backoff. Возможны две наложившиеся друг на друга цепочки старт/стоп после самообновления ядра.

**Что сделать (на выбор, что безопаснее реализовать при чтении окружающего кода — не плодить двойной рестарт):**
- **Вариант А (предпочтительный, если процесс действительно завершается сам после печати `'updater: finished'`):** убрать прямой вызов `stopCore(true)`/`startCore()` из этого блока полностью, оставить только лог/пометку факта обновления. Дать процессу естественно дойти до `'close'`-события — существующий backoff-restart путь (задача A3) и так перезапустит ядро.
- **Вариант Б (если после `'updater: finished'` процесс не гарантированно генерирует `'close'` сам по себе, либо это неочевидно из окружающего кода):** не вызывать `stopCore`/`startCore` синхронно инлайн; отложить вызов вне текущего микротаск/промис-контекста (например, через `setImmediate`/`setTimeout(() => { void restartCore() }, 0)`), чтобы он не пытался встать в очередь лока, пока сам лок ещё держится текущим вызовом. Плюс — добавить флаг-предохранитель (например, `awaitingPostUpdateRestart`), чтобы `'close'`-хендлер не запускал СВОЙ backoff-restart параллельно с этим отложенным вызовом для одного и того же события обновления.
- В любом случае — жёсткое ограничение: нельзя синхронно/инлайн await'ить залоченную (`withCoreLock`-обёрнутую) функцию изнутри ещё не завершившегося вызова той же лок-цепочки.

**Критерий приёмки:** на Windows смоделировать/протрассировать сценарий самообновления ядра (можно вручную вызвать код, эмулирующий появление строки `'updater: finished'` в stdout тестового процесса) — после него в логе (`logPath()`) должна быть ровно одна цепочка stop→start, не две наложившиеся.

### C3. `child` не сбрасывается после ошибки spawn — детектор сети считает мёртвое ядро живым

**Файлы:** `src/main/core/manager.ts:212-221` (обработчик `'error'`, добавлен в задаче A2), `src/main/core/manager.ts:739` (интервал `startNetworkDetection`)

**Проблема:** после неудачного `spawn()` объект `child` создаётся (не `undefined`), но реальный процесс не был запущен — соответственно `child.killed` остаётся `false` (это поле означает "процессу был послан сигнал завершения", а не "процесс не работает"). Проверка на строке 739:
```ts
if ((networkDownHandled && !child) || (child && child.killed)) { ... }
```
после ошибки spawn не срабатывает — `child` truthy и `killed === false` — детектор восстановления сети считает, что ядро в порядке, и не пытается его перезапустить при возврате сети, хотя реально ядро не запущено.

**Что сделать:**
- Ввести отдельный флаг реального состояния процесса (например, `let coreProcessAlive = false`), явно выставлять `true` только после того, как spawn подтверждённо принёс живой процесс (например, сразу после успешного `spawn()`, до появления `'error'`/`'close'`), и сбрасывать в `false` в обработчиках `'error'` и `'close'`.
- Заменить условие на строке 739 (и любые другие места, где `child`/`child.killed` используется как индикатор "ядро сейчас работает" — проверить `stopCoreUnlocked` на строке ~370 отдельно, не трогать её логику остановки, только диагностические проверки живости) на этот флаг.

**Критерий приёмки:** искусственно вызвать ошибку spawn (например, временно испортить `corePath`), затем смоделировать событие "сеть восстановлена" — детектор должен попытаться перезапустить ядро, а не считать его рабочим.

### C4. Grant/Revoke прав падает целиком на macOS/Linux, если alpha-ядро не скачано

**Файл:** `src/main/core/manager.ts` (`manualGrantCorePermition`, `revokeCorePermission`, около строки 460-560 — искать по этим именам)

**Проблема:** после задачи B2 приложение по умолчанию бандлит только stable-ядро. Но `manualGrantCorePermition()`/`revokeCorePermission()`, вызванные без аргументов (так их вызывает `permission-modal.tsx`), всё ещё делают `Promise.all` над обоими `['mihomo', 'mihomo-alpha']`. Если файла `mihomo-alpha` нет на диске — `grantPermission('mihomo-alpha')` бросает исключение, весь `Promise.all` реджектится, хотя право на реально используемое stable-ядро уже успешно выставлено. Пользователь видит общую ошибку в модалке разрешений, `restartCore()` после гранта не вызывается.

**Что сделать:**
- Перед тем как включать ядро в `targetCores` по умолчанию (когда вызов без явного списка `cores`), отфильтровать список только теми ядрами, чей бинарник реально существует на диске (`existsSync(mihomoCorePath(core))`).
- Либо (эквивалентно по эффекту) заменить `Promise.all` на `Promise.allSettled` в `grantPermission`/`revokePermission`-циклах и трактовать как ошибку только фейл по ядру, которое действительно присутствует на диске; отсутствие alpha-бинарника — не ошибка, а штатный skip.
- Не менять сигнатуру `manualGrantCorePermition(cores?: ...)` — доведение до ума именно дефолтного случая (без явных `cores`).

**Критерий приёмки:** на чистой установке без alpha-ядра (дефолтный билд после B2) открыть модалку разрешений на macOS/Linux, нажать "Выдать права" — успешно завершается, `restartCore()` вызывается, ошибки про отсутствующий alpha-бинарник не показывается пользователю.

### C5. Гонка между `initConfig()` и `initFiles()` при первом запуске

**Файл:** `src/main/utils/init.ts` (функция верхнего уровня `init()`, вызывающая `initConfig()` и `initFiles()`; и `initFiles()`/`copyGeodataFiles()`/`activeGeodataFiles()` — реализовано в задаче B1)

**Проблема:** `initConfig()` и `initFiles()` запускаются параллельно (`Promise.all` или аналог) на верхнем уровне. Логика выбора набора геофайлов внутри `initFiles()` синхронно проверяет `existsSync(controledMihomoConfigPath())` до того, как `initConfig()` успевает реально записать этот файл при чистой установке (запись идёт через `await writeFile(...)` внутри `initConfig()`, которая на момент проверки может быть ещё не выполнена). Сейчас это не проявляется только потому, что дефолтное значение `geodata-mode` в `defaultControledMihomoConfig` (template.ts) совпадает с тем, что подставляется как fallback при отсутствии файла — случайное совпадение, не гарантия.

**Что сделать:**
- В `init()` дождаться полного завершения `initConfig()` (`await initConfig()`) до запуска `initFiles()` — то есть сделать эти два шага последовательными, а не параллельными. Небольшая потеря параллелизма на старте некритична (это разовая операция при первом запуске, миллисекунды).
- Не трогать остальную логику `initConfig()`/`initFiles()` — только порядок вызова в `init()`.

**Критерий приёмки:** удалить локально `controledMihomoConfigPath()` файл (эмуляция чистой установки), запустить приложение — набор скопированных геофайлов соответствует реальному дефолтному `geodata-mode` независимо от гонки (проверить логическим трейсом/логом, какой режим был прочитан на момент копирования).

### C6. Дублирование карты платформ `mihomo-alpha` между build-time и runtime

**Файлы:** `scripts/prepare.mjs` (`MIHOMO_ALPHA_MAP`), `src/main/core/downloadCore.ts` (своя копия той же карты)

**Проблема:** одна и та же карта `platform-arch → имя ассета релиза` продублирована буквально в двух местах — одна используется при сборке (`prepare.mjs`, Node ESM скрипт вне TS-компиляции), вторая — при рантайм-докачке alpha-ядра (`downloadCore.ts`, TS в Electron main). Правка в одном месте не гарантированно попадёт во второе.

**Что сделать:**
- Вынести карту в один общий источник, читаемый и сборочным скриптом, и рантайм-кодом. Поскольку `prepare.mjs` — обычный `.mjs` Node-скрипт вне TS build pipeline, а `downloadCore.ts` — TS-модуль в Electron main, самый простой общий формат — JSON-файл (например, `resources/mihomo-platform-map.json` или `scripts/mihomo-platform-map.json`), который `prepare.mjs` читает через `fs.readFileSync`/`import ... with { type: 'json' }`, а `downloadCore.ts` — через обычный `import` JSON-модуля (или тоже `fs.readFileSync`, если сборка TS не сконфигурирована на JSON-импорты — проверить `tsconfig.node.json`/`resolveJsonModule` перед выбором способа).
- Обновить оба места на чтение из этого файла, вместо inline-объектов.
- Не менять состав платформ/имена ассетов — только источник данных.

**Критерий приёмки:** карта платформ существует в одном файле; и `prepare.mjs`, и `downloadCore.ts` используют её оттуда; сборка (`pnpm build:win` как минимум локально по возможности) и рантайм-докачка alpha-ядра продолжают работать на текущих платформах.

## Общие ограничения

- Каждая задача — отдельный коммит.
- Не трогать код вне описанного скоупа, не рефакторить смежные функции "заодно".
- Не менять экспортируемые сигнатуры (`startCore`, `stopCore`, `restartCore`, `waitForCoreReady`, `manualGrantCorePermition`, `revokeCorePermission`) без явной необходимости, отражённой в конкретной задаче.
- После C1-C3 — вручную прогнать сценарий "первый запуск с намеренно битым путём к ядру" и убедиться, что приложение не виснет и показывает диалог ошибки (регрессионная проверка исходной цели TZ_CURSOR.md блока A).
